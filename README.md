# k17-dc4cd

DC4CD-style symbolic distributed processing on a UTXO chain.

Gaglio, Lo Re, Martorella and Peri built DC4CD (ACM TECS 2017): sensor motes that
run Forth as their operating system and cooperate by sending each other Forth
source. This repository ports their two case studies to **K17+**, a Koopman
canonical stack machine hosted in a Bitcoin SV covenant
(<https://github.com/Bittoku/k17-vm>). The UTXO is the message: it carries the program and
its state from hop to hop. The chain supplies what the radio did not — signed
readings, ordering, replay protection, payment for whoever relays, and an audit
trail — at the price of block latency and transaction fees.

## Architecture

[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) describes the components and the security model. It also shows how to build your own machine and how gateways join and leave.

## Disclosures

The K17 design is published as a defensive publication on Technical Disclosure Commons, with two addenda. On-chain anchors on BSV mainnet record the SHA-256 of each document.

Each anchor is a zero-value `OP_FALSE OP_RETURN` output. It pushes the text `K17-ANCHOR`, then a compact JSON object. The JSON holds the SHA-256 of the markdown and PDF of each document, and the source commits in this organisation.

To verify a document:

1. Compute the SHA-256 of the file you downloaded.
2. Open the anchor transaction.
3. Decode the second push of the zero-value output.
4. Compare your hash with the hash in the JSON.

## Run

Requires `../k17-vm` built and compiled first (`cd ../k17-vm && npm test`), since
this package imports its contract artifact.

```bash
npm install
npm test
npm run forth examples/relay.fs
```

History note: `inspect --history` reads 11 unlocking-script chunks. Chunks 7 to 9 are the tree proof of the v3 machine. Chunk 10 is the escrow top-up: a cycle with a top-up shows `top-up <sats>` in its history line, and a cycle with none shows nothing. Machines made before the top-up change do not decode under this artifact (`TEMPLATE_MISMATCH`), the same as pre-v3.1 machines; the rule that a 10-chunk script reads as a top-up of 0 is only a fallback in the decoder. Machines made before v3.1 do not decode under the v3.1 artifact (`TEMPLATE_MISMATCH`), because the dead-man field changed the locking script. A cycle with only 7 chunks (v2) shows as `ambiguous`.

Each command that spends money refuses mainnet without `--i-know-this-spends-real-money`. No command prints the wallet key or a Rabin prime.

## Operational rules

These rules come from the testnet spike and the rehearsal of 2026-10-19.

- A node mines a cycle only when its lock time is below the median time past (MTP). The keeper and the gateway use min(now, MTP - 1). On testnet, MTP is 40 to 50 minutes behind the clock.

- The consortium program reads its round from the lock time. A round closes when the MTP passes the close time. Make `period` much longer than the MTP lag.

- The chain accepts chains of unconfirmed cycles. The tools do not wait for confirmations.

- A live cycle is about 367 KB (k17-vm after the interpreter shrink). The testnet runs here measured about 720 KB and about 720 satoshis before it.

- The tools list wallet coins from WhatsOnChain without the coins that a mempool transaction spends. They retry rate-limited calls (HTTP 429) and reads of a transaction that is not yet indexed.

- The config file keeps the deployment outpoint. The tools follow the machine forward from it.

- Tree mode: the tools refuse a member key that is in the roster already. The chain does not check this, so the roster mirror keeps only the newest leaf for a key. Admit each key once.

- Tree mode: the tools rebuild the roster by replaying every cycle from the genesis inscription. If one cycle cannot be replayed, `admit`, `remove` and the tree gateway stop until the cause is fixed. The funds stay safe: the keeper still halts the machine at its end time, and the dead-man interval refunds the beneficiary.

## The relay in Forth

```
variable sum  variable lo  variable hi
: accumulate ( reading -- )
  dup sum @ + sum !   dup lo @ min lo !   hi @ max hi ! ;
$ffffffff lo !  yield
time DEADLINE - $80000000 and 0= if halt then     \ refund past the deadline
TAG0 in over over 0 sigverify swap drop           \ hop 0: slot 0 attests (TAG0, reading)
150 bounty  accumulate  yield
...
3 out  sum @ out  sum @ 3 / out  lo @ out  hi @ out  halt
```

Each hop is 36 K17 instructions and fits one 40-instruction cycle, so the
attestation check, the bounty and the end of the hop are one transaction.

## Honest limits

- Not a wireless sensor network. Readings reach the chain through a gateway, and a
  hop is a block, not a millisecond. Candidates are control loops with periods of
  minutes or more.
- The interpreter is 183 012 bytes of script at K=40 (43 handlers), and a live cycle
  is about twice that; fees per cycle follow from that, not from the program.
  Shrinking it further is an open engineering item.
- Slot mode keeps a fixed roster in memory (seven landowners). Tree mode keeps an open
  Merkle roster (65 536 leaves) that the sponsor changes with `admit` and `remove`.
- The nChain byte-interpretation patent family reads on the architecture. See
  `k17-vm/CLAUDE.md`; freedom-to-operate opinion before any commercial use.
