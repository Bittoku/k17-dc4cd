# DC4CD §5.1 on a UTXO chain: what the ledger adds and what it costs

Target venue: EuroForth (short paper / talk). Secondary: a workshop on
blockchain-based IoT or mobile code.

## Abstract (draft)

DC4CD (Gaglio, Lo Re, Martorella, Peri, ACM TECS 2017) showed that resource-
constrained sensor nodes can cooperate by exchanging Forth source: a program for
"average temperature" travels along a chain of motes, each adding its reading and
forwarding sum, count and the program itself. Its authors listed security as
future work: any node in radio range may inject any word. We reproduce the §5.1
aggregation experiment on a public UTXO blockchain using K17, a Koopman canonical
stack machine hosted in a Bitcoin SV covenant. The UTXO plays the role of the
in-flight message: it carries program and state from hop to hop, and the chain's
consensus rules supply what the radio did not — authenticated readings (each hop
must be Rabin-signed by the roster member for that hop), ordering and replay
protection (one UTXO, one successor), an incentive for whoever relays, and a
permanent audit trail. The cost is latency (block time instead of milliseconds)
and transaction fees dominated by the interpreter's script size. We report both
and argue that the two systems are the same design in two media.

## 1. DC4CD in one page

- Interpreter is the OS: AmForth on a bare ATmega1281 (IRIS mote), 18.7 KB flash,
  1.3 KB RAM for the whole platform.
- Code travels as text: `<dest> tell: <code> :tell`. The receiver redirects `key`
  to the radio and interprets the payload.
- The message carries its own continuation: `inv: ... :inv` marks the invariant
  part, `~inv` re-injects it, `~` substitutes the sender's top of stack.
- §5.1: average/min over a linear topology with no stored program.
- §5.2: distributed fuzzy fire detection, 31 words, 6 bytes RAM, 863 bytes flash.
- §7: "Future work will focus on ... security aspects."

## 2. K17 in one page

- A UTXO locked by a covenant is a suspended process: program bytes, program
  counter, data stack, return stack, 64 memory cells, 64-cell output log.
- Anyone may spend it; the spend is valid only if the next output carries the same
  program with the state advanced by exactly K=40 instructions, and the spender
  takes no more than the reward the liveness Dutch auction permits at the
  transaction's nLockTime.
- Instruction set: Koopman's Canonical Stack Machine (17) plus HALT, 0=, OUT, TIME,
  the bounty set (IN, VERIFY, BOUNTY, *, HASH, WHO, YIELD) and the K17+ attested-
  input set (MIN, MAX, /, SIGVERIFY).
- `TAG VAL SIGVERIFY k`: valid only if the Rabin signature in the unlocking script,
  under roster key k, signs cell(TAG)||cell(VAL). Rabin because OP_CHECKSIG only
  signs the transaction digest, and Rabin verification is one modular
  multiplication in script.

## 3. The isomorphism

| DC4CD | K17 on BSV |
|---|---|
| Node | Machine UTXO |
| `tell:` frame | Transaction spending the machine |
| Payload = code + data | Program (constant) + witness cells (`IN`) |
| `~` placeholder | Witness cell |
| `inv:`/`~inv` continuation | The next output carries program and state |
| Receiver interprets | Covenant interprets K instructions and enforces the next state |
| Reply is code | Output log read by the next spender; `BOUNTY` payout |
| Radio energy | Fee per cycle |
| No security | Signatures, UTXO consumption, block order, fee as spam price |

## 4. The port

The §5.1 program in the K17 Forth subset (generated by `relaySource`, three hops):

```
variable sum  variable lo  variable hi
: accumulate ( reading -- )
  dup sum @ + sum !   dup lo @ min lo !   hi @ max hi ! ;
$ffffffff lo !  yield
\ hop 0
time DEADLINE - $80000000 and 0= if halt then
EPOCH in over over 0 sigverify swap drop  150 bounty  accumulate  yield
\ hop 1, hop 2: same with slot 1, slot 2
3 out  sum @ out  sum @ 3 / out  lo @ out  hi @ out  halt
```

Each hop is 36 instructions and fits one cycle, so the attestation check, the
bounty and the end of the hop land in one transaction. The output log at HALT is
DC4CD's "retrieval message" to the ancestor: hops, sum, average, min, max.

Differences from the original, stated honestly:
- The program is bytecode, not text. On chain every byte is paid for, and a
  dictionary lookup in script would multiply interpreter cost. Legibility is
  recovered by compiling from Forth source and (optionally) inscribing that source
  beside the machine with its hash as a program literal.
- The hop order is fixed by the program, not discovered by the network. DC4CD's
  setup phase that establishes successor/ancestor links has no analogue here.
- Readings reach the chain through a gateway. This is not a WSN. Only control
  loops with a period of minutes or more are candidates.
- A roster member that never answers would freeze the machine; a deadline lets
  any keeper halt it and refund the deposit. DC4CD has no equivalent failure mode
  because a lost frame simply stops the computation.

## 5. What the ledger adds

1. **Authentication.** A reading is accepted only under the roster key for that
   hop. The relaying keeper is untrusted and is paid by the auction; the attester
   is trusted only for the value.
2. **Ordering and replay protection.** A signature covers (epoch + hop, reading).
   Same roster, different deployment: different epoch. Same deployment, wrong hop:
   wrong tag. The UTXO can be spent once.
3. **Incentive.** `BOUNTY` per hop plus the time-keyed auction reward. Nobody needs
   to run the network; whoever does is paid.
4. **Audit.** Every hop is a transaction; the output log is permanent.

## 6. What it costs (measured)

| Quantity | Value | Source |
|---|---|---|
| Interpreter script, K=40, 32 handlers | 202 468 bytes | k17-vm test "reports the compiled script size", commit f894888 |
| Attestation cycle transaction | 204 130 bytes | k17-vm SIGVERIFY test |
| Per-instruction script cost | about 4.9 KB (SIGVERIFY handler about 0.8 KB) | README measurements |
| Hop latency | one block (about 10 min) or 0-conf | by construction |
| DC4CD fire detector | 31 words, 6 B RAM, 863 B flash | TECS 2017 §5.2 |
| K17 program memory | 256 B memory + 256 B output log | ISA |

Observation: the machine is not the constraint; DC4CD's entire fuzzy system fits
in K17's memory many times over. The fee per cycle is the constraint, and it is a
property of the interpreter's encoding, not of the design.

## 8. Conclusion (draft)

DC4CD moved the interpreter onto the mote so that code could be the message.
K17 moves the interpreter onto the ledger so that the message can be trusted and
paid for. Same stack machine, same two stacks, same tiny memory, same idea of a
program that travels with its data. One trades security for latency and energy;
the other trades latency and fees for security. The interesting engineering is in
the middle: a smaller interpreter (which makes multi-machine `tell:` affordable,
see `inter-machine-tell.md`) and a DC4CD gateway that signs readings as they
leave the radio.
