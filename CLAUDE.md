# k17-dc4cd — agent notes

Port of DC4CD (Gaglio et al., ACM TECS 2017) case studies to the K17+ machine. Read
`README.md` first. Research and design documents live in the Obsidian vault at
`notes/projects/Stack Computers/`; only code, tests, the parked design note and the
held write-up belong here.

## Working rules

- Depends on `../k17-vm` via `file:../k17-vm` and imports its compiled artifact from
  `k17-vm/artifacts/k17Machine.json`. After any ISA change there, run `npm test` in k17-vm
  (build + Docker compile) before running tests here. ISA changes belong in k17-vm, never here.
- `npm test` here runs mocha only; no compile step. Rabin key generation from seed is slow
  (seconds per key), so tests generate attesters once at module level and set long timeouts.
- Programs are written in the Forth subset (`src/forth/compiler.ts`) and generated by
  functions in `src/programs/`. Keep every hop or stage inside one K=40 cycle; the relay test
  asserts this. If a program grows past a cycle, split it at a `yield`, do not raise K.
- The compiler appends `HALT` after top-level code and places colon definitions after it.
- `docs/euroforth-writeup-draft.md` is held until the K17 defensive publication is public
  (decision 2026-10-18: publish first, no provisional filing). Do not publish, post, or send it to
  the DC4CD authors before that, and only on Dave's explicit go.
- Commit messages carry no AI attribution lines (user rule).

## Chain tooling (k17forth)

- Commands: `inspect`, `deploy`, `inscribe-genesis`, `admit`, `remove`, `endorse`, `keeper`, `gateway init|run` (see the README table and
  `docs/tutorial-dc4cd-gateway.md`). `main()` loads the K17Machine artifact for these commands.
- Tests never use the network: the root hook `tests/utils/no-network.ts` (`.mocharc.json`
  `require`) fails any test that calls a non-local host. Inject `provider`, `signer`, `keeper` (chain info, spends lookup)
  and `now` through each command's deps. Consortium fixtures live in
  `tests/utils/consortiumChain.ts`.
- Lock time is always min(now, MTP - 1); never use the wall clock for a lock time. Since v3.1 a cycle
  that keeps the machine alive needs lockTime >= lastTime + 60 (MIN_STEP), and the keeper plans first:
  when `planCycle` throws a MIN_STEP error the tick is `skipped: 'waiting for MTP'` (not an error; the
  chain clock has not moved 60 s past `lastTime`). With MTP - 1 the keeper makes one live cycle per
  block and has no clock lag. The faster mode (lockTime = lastTime + 60, up to about 10 cycles per
  block, but with clock lag) is not implemented. `gateway` and `endorse` use the same `Keeper.tick`, so
  they get the same policy: a lead cycle before the endorsement makes `endorse` report
  `waiting for MTP` until the next block. A halting cycle (fault, HALT, dead-man) is exempt.
  `TickResult.deadManHalt` and the keeper log line ("dead-man halt") report a dead-man refund.
- `deploy --dead-man <seconds>` sets the immutable dead-man interval (0 = off; otherwise at least
  `DEAD_MAN_FLOOR`, 6 h). Use 30 days for daily rounds. `inspect` prints it (`dead-man: off`).
- `makeProvider` lists coins from WhatsOnChain `confirmed/unspent` + `unconfirmed/unspent` and
  drops coins with `isSpentInMempoolTx`. Plain `/unspent` keeps mempool-spent coins and causes
  `txn-mempool-conflict` across processes.
- WhatsOnChain answers 429 and "Not Found" (just after a broadcast) are transient: retry them
  (`retryOn429`, `withRetry`). scrypt-ts providers leave their connection check rejection
  unhandled; the CLI turns "connect failed" into a warning.
- `K17Machine.step` has 10 parameters (the last three are `leafPre`, `proof`, `leafIndex`), and the history
  decoder (`decodeUnlocking` in `src/chain/history.ts`) reads 10 unlocking-script chunks. Pass all three
  from the `CyclePlan`; 7-chunk scripts come from v2 machines and replay as `ambiguous`. Pre-v3.1 machines do not
  decode under the v3.1 artifact (`fromLockingScript` gives TEMPLATE_MISMATCH); the `deadMan` field
  changed the script.
- `admit` and `remove` (tree-mode sponsor) load the roster with `loadRoster` (`src/chain/loadRoster.ts`: genesis inscription + `walkHistory`, checked against the tip's root and seq) and pass the proof through `PendingInput.tree` to `Keeper.tick`. They reload and re-sign once when another cycle lands first, and save `[machine] tip_outpoint` after a relay. `startOutpoint(cfg)` (`tip_outpoint ?? outpoint`) is where every forward-follow starts; `Keeper` uses it, so `keeper` and `gateway` follow from the saved tip too (`admit`, `remove` and the tree-mode gateway write it after a relay).
- `gateway` with `[gateway] mode = "tree"` (`MemberAttester`, `Gateway.handleTreeReading`) is a roster member: it reloads the roster with `loadRoster` before every relay, signs under `readingTag(roundAt(lockTime))` with ONE wall-clock value passed to both `Keeper.chainTime` and `Keeper.tick` (so the lock time is exactly `chain.time`), plans witness `[0, reading]` with `mirror.proofFor(leaf)`, reloads once on a stale proof, and never keeps a signature (a kept reading is signed again for the round of its cycle). Config: `[consortium]` start, period, rounds (no slots/epoch); `GatewayConfig.tree`, `treeOptionsOf`.
- Tree-mode rules. The roster mirror (`RosterMirror` through `loadRoster`: genesis inscription plus a full replay of `walkHistory`, checked against the tip's root and seq) is the only source of roster proofs; never take a leaf or a proof from anywhere else. Rounds are numbered from 1 by `roundAt` (`floor((t - start) / period) + 1`, 0 before `start`); a genesis member has `lastRound` 0, a member admitted in round r has `lastRound` r. Tags: a reading for round r is signed under `0x40000000 + r` (`readingTag`), ADMIT under `0x48000000`, REMOVE under `0x4C000000`. `[machine] tip_outpoint` is the last known tip, written after each relay (`admit`, `remove`, the tree-mode gateway) and cleared on redeploy; `outpoint` stays the deployment; `startOutpoint(cfg)` is `tip_outpoint ?? outpoint`. `genesis_outpoint` is the deployment output and `genesis_inscription` is the roster inscription that `loadRoster` reads; both are written by `deploy --tree` (or `inscribe-genesis` for the inscription).
- `inspect` on a tree machine (`isTreeProgram` or a non-zero `sponsorKeyHash`) prints the tree state; `--genesis <inscription>` or `--config <toml>` gives it the roster (`loadRoster`). `--history` adds the roster table, paid readings, admissions and removals, and the log-hash check (`checkLogHash`) for any program: `DecodedCycle.logged` holds the cells OUTH folded in the cycle (from `CyclePlan.outhCells`), and folding them over the history must give the machine's `logHash`. A mismatch exits 1; an ambiguous cycle gives `not checked`. Paid readings are MEMBER cycles with a `leafAfter`; the round is the new leaf's `lastRound`. An explicit `--genesis` wins over the config's genesis fields, and `--config` gives the network unless `--network` is set.
- The `keeper` command never supplies a roster-tree proof to `planCycle`, so it cannot relay MEMBER,
  ADMIT or REMOVE cycles yet; on such a machine it reports `plan: ...` and broadcasts nothing (fails safe).
  Tree-mode relaying is a later plan.
- Testnet only for live runs. Secrets (WIF, Rabin primes) never go into logs, docs or notes.
